# RapidHash V3 versus Wyhash

Before: a91033a. After: the commit that adds this capture.
Both builds use Zig 0.16.0, ReleaseSafe, and the native Neoverse-V3 CPU target.
The host is aarch64-linux, Linux 7.2.7, benchstat from goperf in nixpkgs.

## Raw hash

Five million hashes per length. The loop also mutates one input byte per
iteration to keep the hash live, so the absolute values include that write.
Two runs produced the same figures within 1%.

| Bytes | Wyhash ns | RapidHash ns | RapidHash / Wyhash |
|---:|---:|---:|---:|
| 8 | 4.22 | 3.62 | 0.86 |
| 16 | 3.94 | 3.62 | 0.92 |
| 32 | 3.78 | 3.75 | 0.99 |
| 64 | 4.24 | 4.06 | 0.96 |
| 128 | 6.32 | 6.69 | 1.06 |
| 255 | 10.85 | 10.29 | 0.95 |
| 512 | 21.96 | 18.97 | 0.86 |

## Reading

Raw RapidHash is faster for the short keys DNS uses most often and for large
keys, and about 6% slower at 128 bytes. The end-to-end cache path pays 0.72%
geomean. The pipeline row is neutral. The index geomean is 5.34% slower, driven
by one synthetic full-miss key at capacities 10000 and 100000 that lands in a
different probe cluster. The other test keys move in both directions.

The change removes the second 64-bit hash implementation from the binary. The
capture retains the regression so a later index redesign can compare against it.
